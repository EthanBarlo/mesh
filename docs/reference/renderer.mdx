A renderer is a plain object that teaches Mesh to mount one framework's components. React, Vue and
Svelte ship as `@mesh/react`, `@mesh/vue` and `@mesh/svelte`; each renderer is under eighty lines,
because the Mesh core does everything that is the same across frameworks. Their default exports are
[lazy renderers](#lazy-renderers), so a framework only downloads on pages that need it, and each has
a factory for [app-level setup](#built-in-renderer-options). This page is the contract. For a
walkthrough of writing one, see [Custom renderers](/docs/advanced/custom-renderers).

## MeshRenderer

```ts
type MeshRenderer<TNode = unknown> = {
    type: string;
    extensions?: string[];
    nativeSlots?: boolean;
    renderSlot: SlotRenderer<TNode>;
    mount: (args: {
        el: HTMLElement;
        livewireComponent: LivewireComponent;
        Component: any;
        ctx: RenderContext<TNode>;
    }) => {
        update: (ctx: RenderContext<TNode>) => void;
        cleanup: () => void;
    };
};
```

`TNode` is whatever your framework uses to represent a piece of slot content: a `ReactNode` for
React, a slot function for Vue, a `Snippet` for Svelte.

The core picks a component's renderer from its entry file's extension. A renderer with
`type: 'react'` replaces the built-in React renderer for every `.tsx` and `.jsx` component; a
renderer for another framework lists the extensions it owns in `extensions`. See
[Claiming a file extension](/docs/advanced/custom-renderers#claiming-a-file-extension).

## Lazy renderers

`renderers` in `initMesh` also accepts a lazy descriptor: the type, any extensions, and a function
that loads the real renderer.

```ts
type LazyMeshRenderer = {
    type: string;
    extensions?: string[];
    load: () => Promise<MeshRenderer<any>>;
};
```

This is what `@mesh/react`, `@mesh/vue` and `@mesh/svelte` export. The descriptor module imports no
framework code, and `load()` is a dynamic `import()` of the renderer, so Vite puts the framework
runtime in its own chunk instead of the entry bundle.

- The core calls `load()` the first time an island of that type mounts, never at start-up. A page
  without islands of that type never calls it.
- It calls `load()` once per descriptor. Every island of that type waits on the same promise and
  shares the renderer.
- It loads the renderer and the component's chunk in parallel, and mounts once both are in.
- If `load()` rejects, or resolves to something without `mount`, the island logs
  `Mesh: failed to render "<id>"` with the error, and the next island of that type calls `load()`
  again.

A full renderer object is still accepted anywhere a descriptor is. Write your own descriptor when a
custom renderer should load lazily too:

```ts title="resources/js/app.ts"
initMesh(Livewire, {
    renderers: [
        {
            type: 'marko',
            extensions: ['marko'],
            load: () => import('./renderers/marko').then((m) => m.default),
        },
    ],
});
```

## Built-in renderer options

Each framework entry exports a factory that builds its lazy descriptor with app-level options. The
default export is the factory called with no options, so these two lines are equivalent:

```ts
import reactRenderer, { createReactRenderer } from '@mesh/react';

const sameAsDefault = createReactRenderer();
```

Every island is its own root or app, so the options apply once per island.

The factory defers the framework and the renderer, not your options. Whatever the options import
(the providers, plugins or stores above, and React itself for the JSX) is imported by `app.ts`, so
it is in the entry chunk. To keep it lazy too, load the module that calls the factory from a
descriptor of your own; the factory's `load()` returns the configured renderer:

```ts title="resources/js/app.ts"
initMesh(Livewire, {
    renderers: [
        {
            type: 'react',
            load: () => import('./renderers').then((m) => m.reactRenderer.load()),
        },
    ],
});
```

Each factory's options type is exported too: `ReactRendererOptions`, `VueRendererOptions` and
`SvelteRendererOptions`.

## RenderContext and slots

```ts
type RenderContext<TNode> = {
    props: Record<string, any>;
    slots: PreparedSlots<TNode>;
};

type PreparedSlots<TNode> = {
    children: TNode | undefined;
    named: Record<string, TNode>;
    hasNamed: boolean;
};

type SlotRenderer<TNode> = (html: string, name: string) => TNode;

type MeshSlots = Record<string, string>;
```

    },

    },
    'slots.hasNamed': {
      type: 'boolean',
      description: 'true when there is at least one named slot.',
    },
  }}
/>

The core reads slot HTML from the direct children of the hidden `[data-mesh-slots]` holder
(`MeshSlots`, keyed by name, the unnamed slot as `default`) and strips Livewire's fragment marker
comments before handing it to `renderSlot`.

**`renderSlot` must be pure.** The core calls it once per slot, outside any mount, before the first
`mount` and again for every slot whenever slot content changes. It cannot depend on per-mount
state. Every built-in renderer wraps the HTML in `<div style="display: contents">` so the wrapper
does not take part in layout.

## Reserved props and nativeSlots

React and Svelte pass slots through props (`children` and `slots`), so a prop with one of those
names would silently replace slot content. Before `mount` and before every `update`, the core
checks:

| Condition | Error |
| --- | --- |
| Any slot present and `"children" in props` | ``Mesh: `children` is reserved for slot content — rename the prop from props().`` |
| Named slots present and `"slots" in props` | ``Mesh: `slots` is reserved for named slot content — rename the prop from props().`` |

A renderer that delivers slots through a native API, as Vue does with `<slot>`, sets
`nativeSlots: true` and the check is skipped. A `slots` prop is always fine when only the default
slot is used.

## Who owns what

| The Mesh core | The renderer |
| --- | --- |
| Discovering entries and building the registry | `type`, `extensions` |
| Loading the lazy chunk, caching it, retrying a failed load | `renderSlot(html, name)` |
| Loading a lazy renderer once, before its first mount | `mount(...)` |
| Checking for a default export | `update(ctx)` |
| Reading `data-mesh-props` and the slot holders | `cleanup()` |
| Finding `.mesh-root` | Providing `livewireComponent` to the framework's context |
| Splitting default and named slots | Wrapping slot HTML so it does not affect layout |
| The reserved-prop check | |
| Dirty-checking props | |
| Watching slot holders with a `MutationObserver` | |
| Teardown, including teardown during a load | |
| Catching and logging errors | |

## The update contract

What the core guarantees about calls to `update` and `cleanup`:

- **Full context, every time.** `update` always receives complete props and complete prepared slots,
  never a diff.
- **Props-only updates reuse slot nodes.** After a Livewire morph the core re-reads
  `data-mesh-props` and compares it with the last props as JSON. Identical JSON is a no-op. Otherwise
  `update` receives the new props and the **same** `slots` object as before, with the same node
  references, so a reconciler can skip unchanged slot content.
- **Slot updates re-render every slot.** When the slot holders change, the core runs `renderSlot` for
  every slot again and calls `update` with fresh slots and the current props.
- **Validate, then commit.** The core only adopts new props or slots after the reserved-prop check
  and your `update` both succeed. If `update` throws, the error is logged (`Mesh: failed to update
  props` or `Mesh: failed to update slots`) and the previous state stays the baseline, so the next
  identical morph tries again instead of being skipped.
- **Mount failures are contained.** If `mount` throws, the core logs `Mesh: failed to render "<id>"`
  with the error; other islands are unaffected.
- **Cleanup is wired before loading.** The core registers its teardown with Livewire before it starts
  loading the chunk and the renderer. If Livewire removes the component while either loads, `mount`
  is never called.
- **Teardown forgets the island.** When Livewire removes a mounted island, the core calls `cleanup`
  and removes the island from `window.Mesh.renderedComponents`.

For frameworks that re-render from the top (React), `update` can simply render again. For frameworks
that mount once and then mutate state (Vue, Svelte), `update` assigns the new context into reactive
state created in `mount`. Both shapes are walked through in
[Custom renderers](/docs/advanced/custom-renderers).
