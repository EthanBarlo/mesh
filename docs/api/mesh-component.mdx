# `Mesh\Component`

Every Mesh component is a PHP class extending `EthanBarlo\Mesh\Component`. It declares the props passed to the frontend and the **id** that links to the JS component.

## Minimal component

```php
<?php

namespace App\Mesh;

use EthanBarlo\Mesh\Component;

class Counter extends Component
{
    public function props(): array
    {
        return [
            'start' => 0,
        ];
    }
}
```

## `props(): array`

Returns the associative array of props handed to the frontend component. Values must be JSON-serializable. Called once per render.

```php
public function props(): array
{
    return [
        'start' => $this->start,
        'label' => 'Clicks',
    ];
}
```

## `component(): string`

Returns the component **id** — a simple string like `Counter` or `Forms/Input`. By default it is
auto-derived from the class name, so you rarely write it yourself.

```php
// Default for App\Mesh\Counter — you don't need to write this.
public function component(): string
{
    return 'Counter';
}
```

## How the id is derived

The default `component()` derives the id from the class name relative to the `App\Mesh` namespace:
it strips the `App\Mesh\` prefix and replaces the remaining backslashes with forward slashes.

- `App\Mesh\Counter` → `Counter`
- `App\Mesh\Forms\Input` → `Forms/Input`

The JS side derives the identical id from the component's folder under the fixed `resources/js/mesh`
directory (`/resources/js/mesh/Forms/Input/index.tsx` → `Forms/Input`). Because `make:mesh`
StudlyCases both the class segments and the folder names, the two sides always agree.

You can override `component()` to return any id, but it must match a component Mesh discovers under
`resources/js/mesh`.

## Nested components

For `App\Mesh\Forms\Input`, the derived id is `Forms/Input`. The JS entry lives at
`resources/js/mesh/Forms/Input/index.tsx` and resolves to the same id automatically.

## Slots

Inner content of a `<mesh:…>` tag is forwarded to the frontend as React `children`, and named slots
arrive in a `slots` prop. You write nothing extra on the PHP class — capturing slots is automatic.

```blade
<mesh:card>
    <livewire:slot name="title">Welcome</livewire:slot>
    Hello <strong>{{ $name }}</strong>
</mesh:card>
```

```tsx
export default function Card({
    children,
    slots,
}: {
    children?: React.ReactNode;
    slots?: { title?: React.ReactNode };
}) {
    return (
        <section>
            <h2>{slots?.title}</h2>
            <div>{children}</div>
        </section>
    );
}
```

The **default slot** (everything not inside a named `<livewire:slot>`) becomes `children`. **Named
slots** become entries on the `slots` prop, keyed by name. Use the `name="title"` form — Livewire 4
has no `:title` slot shorthand.

Slot content is **reactive to the server**: when a parent re-render changes the slot (for example a
slot that interpolates parent state), Mesh replaces the rendered content. It is rendered **statically**
from server HTML, so **nested interactive Livewire/Alpine inside a slot is not supported in v1** — pass
interactive children as their own Mesh components or props instead.

<Callout type="warn">
  **Security:** slot content is mirrored into the page with `dangerouslySetInnerHTML`. Blade escapes
  `{{ }}` interpolation, so slots built from `{{ … }}` are safe. Content written with `{!! … !!}` (or
  any other unescaped output) is injected as raw HTML — never put unsanitised user input in a slot.
</Callout>

`children` and `slots` are **reserved** prop names. Mesh throws when `props()` returns a `children`
key while any slot is present, or a `slots` key while named slots are present, so the collision can't
silently shadow the slot content. (A `slots` prop is fine when only the default slot is used — Mesh
only passes the `slots` prop for named slots.)

### `meshSlots(): array`

An `@internal` helper that returns the real slot content keyed by name (the default slot is named
`default`). It is populated on the mount render only; on the component's own re-render the slots become
content-less placeholders and it returns `[]`. You won't normally call this — it backs the Blade view
and the slot tests.

## How rendering works

1. Blade renders `<mesh:counter />`, which compiles to a namespaced Livewire mount.
2. Mesh calls `component()` to get the id and `props()` to get the data.
3. The id is emitted to the runtime, which looks it up in the lazy component registry Mesh builds by
   auto-discovering every entry under `resources/js/mesh`.
4. The runtime imports that component's code-split chunk on first render, then mounts it with the
   props using the renderer inferred from the entry's file extension.

## Case sensitivity

Component ids are case-sensitive. `App\Mesh\Counter` maps to the `Counter/` folder, not `counter/`. On case-insensitive filesystems (macOS) a mismatch can hide until it surfaces on Linux. Always keep the folder name byte-identical to the StudlyCase class name.

## Props lifecycle

Props are computed server-side in `props()` and serialized into the mount payload. They are not reactive after mount unless you re-render the Livewire component (which re-runs `props()` and re-mounts/updates the island).
