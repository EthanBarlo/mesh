title: Custom renderers
description: How the three shipped renderers work, how to replace one or add a framework with its own file extension, and how to keep a custom renderer lazy.
---

A renderer is the small adapter between Mesh and a UI framework: it turns slot HTML into the
framework's nodes and mounts, updates and unmounts a component. The contract is on the
[Renderer API](/docs/reference/renderer) page. This page reads the shipped renderers line by line,
then shows how to add a renderer of your own.

<Callout title="Only need providers, plugins or context?">
  You probably don't need a custom renderer. `createReactRenderer({ wrap, strictMode })`,
  `createVueRenderer({ setup })` and `createSvelteRenderer({ context })` cover app-level setup. See
  [Built-in renderer options](/docs/reference/renderer#built-in-renderer-options).
</Callout>

## What a custom renderer can do

The core picks a component's renderer from its entry file's extension. The built-in mapping is
`tsx` and `jsx` to `react`, `vue` to `vue` and `svelte` to `svelte`, and a renderer's `extensions`
adds to it:

```ts title="resources/js/buildRegistry.ts (inferRenderer, simplified)"
const map = { tsx: 'react', jsx: 'react', vue: 'vue', svelte: 'svelte' };
for (const renderer of renderers) {
    for (const ext of renderer.extensions ?? []) map[ext] = renderer.type;
}
if (ext in map) return map[ext];
throw new Error('Mesh: cannot infer renderer for component entry …');
```

That means:

- **You can replace a built-in renderer.** A renderer whose `type` is `'react'`, `'vue'` or
  `'svelte'` takes over every component with that extension. Pass it to `initMesh` instead of the
  built-in one (if you pass both, the one listed last wins).
- **You can add a framework with its own file type.** Give the renderer a new `type`, claim its
  extension in `extensions`, and glob its entries through `sources`. See
  [Claiming a file extension](#claiming-a-file-extension).
- **A claim beats the built-in mapping.** A Solid renderer with `extensions: ['tsx']` takes every
  `.tsx` entry away from React, so only do that in an app with no React islands. When two configured
  renderers claim one extension, the one listed last wins.
- **You cannot pick a renderer per component.** The PHP side carries only an id and props; the
  extension decides.

## Claiming a file extension

Say you have a renderer for a framework whose components are `.marko` files. Wire it up in three
parts: the renderer claims the extension, a lazy descriptor keeps it out of the entry chunk, and a
glob of your own finds the entries.

```ts title="resources/js/app.ts"
import { Livewire } from
    '../../vendor/livewire/livewire/dist/livewire.esm';
import { initMesh } from '@mesh';
import reactRenderer from '@mesh/react';

initMesh(Livewire, {
    renderers: [
        reactRenderer,
        {
            type: 'marko',
            extensions: ['marko'],
            load: () => import('./renderers/marko').then((m) => m.default),
        },
    ],
    sources: [import.meta.glob('/resources/js/mesh/**/index.marko')],
});

Livewire.start();
```

- **`extensions`** maps `.marko` entries to the `marko` type. Write it without the dot. It can sit on
  the lazy descriptor, as here, or on a full renderer object.
- **The glob is yours.** Mesh's own discovery glob is the literal
  `/resources/js/mesh/**/index.{tsx,jsx,vue,svelte}`. Vite only accepts literal patterns, so Mesh
  cannot add your extension to it at runtime. Glob the entries yourself and pass the result in
  `sources`.
- **Ids work the same.** The extension is stripped whatever it is, then a trailing `/index`, so
  `resources/js/mesh/Clock/index.marko` is `Clock`. Entries in the app's own `resources/js/mesh`
  share one id space with the discovered ones: `Clock/index.tsx` next to `Clock/index.marko` is a
  duplicate, and the first one found keeps the id.
- **The PHP side is unchanged.** The class is an ordinary `Mesh\Component`. `make:mesh` only knows
  the built-in frameworks, so create the entry file by hand.
- **The module `./renderers/marko`** default-exports a `MeshRenderer` built like the walkthroughs
  below. It should provide `livewireComponent` through the framework's own context mechanism so your
  components can reach `$wire`. Keep it outside `resources/js/mesh`, which is for components.

Passing the renderer object itself instead of a descriptor also works, but then the framework is in
the entry chunk on every page.

## Walkthrough: React

`@mesh/react`'s default export is a lazy descriptor whose `load()` imports this module. The renderer
itself, simplified: imports and the `wrap` and `strictMode` options are left out.

```tsx title="resources/js/react/slot.tsx and renderer.tsx (simplified)"
export function MeshSlot({ html }: { html: string }) {
    return (
        <div
            style={{ display: 'contents' }}
            dangerouslySetInnerHTML={{ __html: html }}
        />
    );
}

const reactRenderer: MeshRenderer<React.ReactNode> = {
    type: 'react',

    renderSlot: (html, name) => (
        <MeshSlot
            key={name === 'default' ? undefined : name}
            html={html}
        />
    ),

    mount: ({ el, livewireComponent, Component, ctx }) => {
        const root = createRoot(el);

        const render = ({
            props,
            slots,
        }: RenderContext<React.ReactNode>) => {
            const named = slots.hasNamed ? { slots: slots.named } : {};

            root.render(
                <React.StrictMode>
                    <LivewireContext.Provider value={livewireComponent}>
                        <Component {...props} {...named}>
                            {slots.children}
                        </Component>
                    </LivewireContext.Provider>
                </React.StrictMode>,
            );
        };

        render(ctx);

        return { update: render, cleanup: () => root.unmount() };
    },
};
```

Reading it top to bottom:

1. **`MeshSlot`** is the slot node. React fragments cannot take `dangerouslySetInnerHTML`, so the
   HTML needs a host element; `display: contents` keeps that element out of layout.
2. **`renderSlot`** keys named slots by name so React keeps their identity across renders. The
   default slot becomes `children` and needs no key. It does nothing but build an element, which
   keeps it pure.
3. **`mount`** creates one root per island in `el`, the empty `.mesh-root`.
4. **`render`** is used for both the first paint and every update. In React, updating is rendering
   again; the reconciler works out what changed. Because the core passes the same slot elements on
   props-only updates, React skips the slot subtrees.
5. **`LivewireContext.Provider`** is what makes `useWire()` and the other hooks work. A replacement
   renderer must provide it.
6. **`cleanup`** unmounts the root when Livewire removes the component.

## Mount once, then mutate: Vue

Vue does not re-render from the top. It mounts an app once and reacts to state changes, so the
renderer keeps the context in reactive state and `update` writes into it (simplified: the `setup`
option is left out):

```ts title="resources/js/vue/slot.ts and renderer.ts (simplified)"
export type VueSlot = () => VNodeChild;

export const renderSlotHtml = (html: string): VueSlot => () =>
    h('div', { style: 'display: contents', innerHTML: html });

const vueRenderer: MeshRenderer<VueSlot> = {
    type: 'vue',
    nativeSlots: true,

    renderSlot: (html) => renderSlotHtml(html),

    mount: ({ el, livewireComponent, Component, ctx }) => {
        const state = shallowReactive<RenderContext<VueSlot>>({
            props: ctx.props,
            slots: ctx.slots,
        });

        const app = createApp({
            render: () =>
                h(Component, { ...state.props }, {
                    ...(state.slots.children
                        ? { default: state.slots.children }
                        : {}),
                    ...state.slots.named,
                }),
        });

        app.provide(LivewireComponentKey, livewireComponent);
        app.mount(el);

        return {
            update: (next) => {
                state.props = next.props;
                state.slots = next.slots;
            },
            cleanup: () => app.unmount(),
        };
    },
};
```

What is different from React:

- **`renderSlot` returns a function, not a vnode.** Vnodes are single-use, but a Vue slot *is* a
  function that returns vnodes. A stable function is exactly what the core keeps across props-only
  updates.
- **`nativeSlots: true`.** Slots go to Vue's own slot system (`<slot />`, `<slot name="…" />`), so
  `children` and `slots` are ordinary props and the core skips the reserved-prop check.
- **`shallowReactive` state.** The core replaces `props` and `slots` wholesale on every update, so a
  shallow wrapper is enough to trigger a re-render, and server props are not deep-proxied.
- **`app.provide`.** Each island is its own app, so an app-level provide reaches every component
  inside it. The key must be the `LivewireComponentKey` exported from `@mesh/vue`; it is what the
  composables `inject`.

## Svelte: state you can assign into

The Svelte renderer has the same mount-once shape. Svelte components take everything as props, so
it flattens the context into a single props object kept in `$state` (simplified: the `context`
option is left out):

```ts title="resources/js/svelte/slot.ts and renderer.svelte.ts (simplified)"
export const renderSlotHtml = (html: string): SvelteSlot =>
    createRawSnippet(() => ({
        render: () => `<div style="display: contents">${html}</div>`,
    }));

const flattenContext = (ctx: RenderContext<SvelteSlot>) => ({
    ...ctx.props,
    ...(ctx.slots.children ? { children: ctx.slots.children } : {}),
    ...(ctx.slots.hasNamed ? { slots: ctx.slots.named } : {}),
});

const svelteRenderer: MeshRenderer<SvelteSlot> = {
    type: 'svelte',

    renderSlot: (html) => renderSlotHtml(html),

    mount: ({ el, livewireComponent, Component, ctx }) => {
        const props: Record<string, any> = $state(flattenContext(ctx));

        const app = mount(Component, {
            target: el,
            props,
            context: new Map([
                [LivewireComponentKey, livewireComponent],
            ]),
        });

        return {
            update: (next) => {
                const flat = flattenContext(next);
                for (const key of Object.keys(props)) {
                    if (!(key in flat)) delete props[key];
                }
                Object.assign(props, flat);
            },
            cleanup: () => unmount(app),
        };
    },
};
```

- **The file is `renderer.svelte.ts`.** `$state` is a rune, and runes only compile in files the
  Svelte plugin processes. A Svelte renderer of your own needs the same suffix.
- **`createRawSnippet`** turns HTML into a snippet. It must render a single root element, which is
  another reason for the `display: contents` wrapper.
- **Slots mirror React, not Vue.** The default slot is the `children` snippet and named slots are a
  `slots` record, so `nativeSlots` is left off and the reserved-prop check applies.
- **`update` deletes keys that disappeared** (for example a slot that emptied out) before assigning
  the rest, because both deletions and assignments are tracked by the `$state` proxy.
- **Context goes through `mount`'s `context` option**, keyed by the `LivewireComponentKey` from
  `@mesh/svelte`.

## Example: shared providers

The most common reason to touch a renderer is to put something around every island: a theme, a
data-fetching client, an error boundary. Each island is its own root, so the renderer is the only
place to do it. The built-in factories take that as an option, so you do not need to copy a
renderer:

```tsx title="resources/js/renderers.tsx"
import { createReactRenderer } from '@mesh/react';
import { AppProviders } from '@/providers';

export const reactRenderer = createReactRenderer({
    wrap: (island) => <AppProviders>{island}</AppProviders>,
});
```

```ts title="resources/js/app.ts"
import { Livewire } from
    '../../vendor/livewire/livewire/dist/livewire.esm';
import { initMesh } from '@mesh';
import { reactRenderer } from './renderers';

initMesh(Livewire, {
    renderers: [reactRenderer],
});

Livewire.start();
```

`wrap` runs inside Mesh's context, so `AppProviders` can use `useWire()`. Anything created at module
scope in `@/providers` (a client, a store) is created once and shared by every island on the page,
while each island still gets its own provider instance. `createReactRenderer({ strictMode: false })`
drops StrictMode the same way.

The Vue version passes `setup`, which runs on each island's app before it mounts:

```ts
import { createVueRenderer } from '@mesh/vue';

export const vueRenderer = createVueRenderer({
    setup: (app) => installPlugins(app), // your function: app.use(...), app.component(...)
});
```

Every island is a separate app, so `installPlugins` runs once per island. Whether one plugin
instance can be installed on several apps depends on the plugin; when in doubt, create one per call.
Svelte's factory takes `context`, a function returning a `Map` that is merged into each island's
mount context.

Whatever `renderers.tsx` imports ends up in the entry chunk, because `app.ts` imports it. To keep the
providers lazy too, see [Built-in renderer options](/docs/reference/renderer#built-in-renderer-options).
Write a renderer of your own only for what the options do not cover, and keep renderer files out of
`resources/js/mesh`.

## Testing a renderer

Mesh's own renderer tests (`tests/js/reactRenderer.test.ts`, `vueRenderer.test.ts` and
`svelteRenderer.test.ts`) mount a real component through the core's `mountComponent` with a
hand-built context. They are a good template. A
renderer should pass the same checks:

- mounts a component with props;
- renders the default slot HTML inside a `display: contents` wrapper;
- exposes named slots the way your framework expects;
- re-renders in place on a props update, without remounting;
- swaps slot content on a slot update;
- unmounts on `cleanup`;
- makes the Livewire component available to `useLivewireComponent`.
