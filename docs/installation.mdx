## Requirements

- PHP 8.3 or newer
- Laravel 11 or 12
- Livewire 4
- Node and Vite, with `laravel-vite-plugin`
- At least one of React 18+, Vue 3.3+, or Svelte 5

Mesh hooks into the Livewire instance your own bundle imports, so the app
bundles Livewire itself (Livewire's "manual bundling" setup). The steps
below cover that.

## Install

<Steps>
<Step>

### Require the package

```bash
composer require ethanbarlo/mesh
```

Laravel discovers the service provider. It registers the `<mesh:…>` Blade
tag, a `mesh` Livewire namespace that points at `App\Mesh`, and the
`make:mesh` command. There is no npm package to install for Mesh itself.

</Step>
<Step>

### Install your framework and its Vite plugin

<Frameworks>
<Tab value="React">

```bash
npm install react react-dom
npm install -D @vitejs/plugin-react
```

</Tab>
<Tab value="Vue">

```bash
npm install vue
npm install -D @vitejs/plugin-vue
```

</Tab>
<Tab value="Svelte">

```bash
npm install svelte
npm install -D @sveltejs/vite-plugin-svelte
```

The scaffolded components use `<script lang="ts">`. Svelte 5 strips type
annotations on its own, so no preprocessor is needed. Only TypeScript that
emits code, such as `enum`, needs `vitePreprocess` with `script: true`:

```js title="svelte.config.js"
import { vitePreprocess } from '@sveltejs/vite-plugin-svelte';

export default {
    preprocess: vitePreprocess({ script: true }),
};
```

</Tab>
</Frameworks>

</Step>
<Step>

### Add the plugin and the `@mesh` alias to Vite

<Frameworks>
<Tab value="React">

```ts title="vite.config.ts"
import { defineConfig } from 'vite';
import laravel from 'laravel-vite-plugin';
import react from '@vitejs/plugin-react';

export default defineConfig({
    plugins: [
        laravel({
            input: ['resources/css/app.css', 'resources/js/app.ts'],
            refresh: true,
        }),
        react(),
    ],
    resolve: {
        alias: {
            '@mesh': '/vendor/ethanbarlo/mesh/resources/js',
        },
    },
});
```

</Tab>

Components are not Vite inputs. Mesh discovers them itself, so `input`
lists only your real entry points.

</Step>
<Step>

### Start Livewire and Mesh in `app.ts`

<Frameworks>
<Tab value="React">

```ts title="resources/js/app.ts"
import {
    Livewire,
    Alpine,
} from '../../vendor/livewire/livewire/dist/livewire.esm';
import { initMesh } from '@mesh';
import reactRenderer from '@mesh/react';

initMesh(Livewire, {
    renderers: [reactRenderer],
    debug: import.meta.env.DEV,
});

Livewire.start();
```

</Tab>
<Tab value="Vue">

```ts title="resources/js/app.ts"
import {
    Livewire,
    Alpine,
} from '../../vendor/livewire/livewire/dist/livewire.esm';
import { initMesh } from '@mesh';
import vueRenderer from '@mesh/vue';

initMesh(Livewire, {
    renderers: [vueRenderer],
    debug: import.meta.env.DEV,
});

Livewire.start();
```

</Tab>
<Tab value="Svelte">

```ts title="resources/js/app.ts"
import {
    Livewire,
    Alpine,
} from '../../vendor/livewire/livewire/dist/livewire.esm';
import { initMesh } from '@mesh';
import svelteRenderer from '@mesh/svelte';

initMesh(Livewire, {
    renderers: [svelteRenderer],
    debug: import.meta.env.DEV,
});

Livewire.start();
```

</Tab>
</Frameworks>

Call `initMesh()` before `Livewire.start()`. It builds the component
registry and registers its Livewire hooks synchronously, so they are in
place before Livewire initializes the first component. `debug` logs
discovery and every mount to the console; `import.meta.env.DEV` keeps it out
of production builds. Every option is described in the
[`initMesh` reference](/docs/reference/init-mesh).

</Step>
<Step>

### Load the bundle from your layout

```blade title="resources/views/components/layouts/app.blade.php"
<!DOCTYPE html>
<html lang="{{ str_replace('_', '-', app()->getLocale()) }}">
<head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>{{ $title ?? config('app.name') }}</title>

    @livewireStyles
    @vite(['resources/css/app.css', 'resources/js/app.ts'])
</head>
<body>
    {{ $slot }}

    @livewireScriptConfig
</body>
</html>
```

Use `@livewireScriptConfig`, not `@livewireScripts`. Your bundle already
contains Livewire; the directive only prints the configuration that copy
reads when `Livewire.start()` runs.

<Callout type="warn" title="The step people miss">
  Without `@livewireScriptConfig`, Livewire injects its own copy of its
  script, so two copies of Livewire and Alpine run on the page. The console
  warns about multiple instances, and behaviour becomes unreliable. With
  `inject_assets` turned off, your bundle has no update URI and every request
  fails.
</Callout>

</Step>
<Step>

### Check the setup

Run `npm run dev` and open any page that uses the layout. With no
components yet, the browser console shows a warning that begins
`Mesh: no components found under resources/js/mesh`. That warning means the
runtime loaded and its hooks are registered. The
[Quickstart](/docs/quickstart) creates the first component.

</Step>
</Steps>

## Mixing renderers

Each component's renderer comes from its file extension, so one app can mix
frameworks. Install each framework and its Vite plugin, add every plugin to
`vite.config.ts`, and register every renderer:

```ts title="resources/js/app.ts"
import { initMesh } from '@mesh';
import reactRenderer from '@mesh/react';
import vueRenderer from '@mesh/vue';
import svelteRenderer from '@mesh/svelte';

initMesh(Livewire, {
    renderers: [reactRenderer, vueRenderer, svelteRenderer],
    debug: import.meta.env.DEV,
});
```

- `make:mesh` uses React unless told otherwise. Pass `--renderer=vue` or
  `--renderer=svelte`, or change the default in `config/mesh.php`.
- Registering a renderer costs almost nothing up front. Each is a small
  lazy descriptor, and its framework's runtime downloads the first time an
  island of that kind mounts, so a page only loads the frameworks its
  islands use.
- A component whose renderer isn't registered fails to mount, and the
  console logs `Mesh renderer for "vue" not found`.

## The `@mesh` alias

The JavaScript runtime ships inside the Composer package, at
`vendor/ethanbarlo/mesh/resources/js`. The alias points Vite at it instead
of at an npm package, so `composer update ethanbarlo/mesh` updates the PHP
and JavaScript halves together and they can never drift apart.

| Import | What it provides |
| --- | --- |
| `@mesh` | `initMesh` and the public types, such as `Wire` and `MeshRenderer` |
| `@mesh/react` | The React renderer (default export), `createReactRenderer`, `useWire`, `useEntangle`, `useErrorBag` |
| `@mesh/vue` | The Vue renderer, `createVueRenderer` and the same three composables |
| `@mesh/svelte` | The Svelte renderer, `createSvelteRenderer` and the same three, built on runes |

Two consequences are worth knowing:

- **`vendor/` must exist before Vite runs.** Vite reads Mesh, and Livewire's
  ESM build, from `vendor/`. In CI or a Docker build, run `composer install`
  before `npm run build`.
- **Your app provides the framework.** The runtime imports `react`, `vue`,
  or `svelte`, and Vite resolves them from your app's `node_modules`. They
  are optional peer dependencies of Mesh, which is why you installed them
  yourself.

The alias above is root-relative. The demo apps write the same thing as
`path.resolve(__dirname, 'vendor/ethanbarlo/mesh/resources/js')`.

## Configuration

Publishing the config is optional:

```bash
php artisan vendor:publish --tag=mesh-config
```

```php title="config/mesh.php"
return [
    'make' => [
        // 'react', 'vue' or 'svelte'
        'renderer' => 'react',
    ],
];
```

That is the only option: the renderer `make:mesh` scaffolds when you don't
pass `--renderer`. The component directory is fixed at `resources/js/mesh`
on purpose. Both halves derive the component id from that path, so keeping
it fixed means the PHP class, the frontend folder, and the discovery glob
always agree. Components shipped in Composer packages are added with the
`sources` option of `initMesh`; see
[Components in Composer packages](/docs/guides/packages).

## TypeScript

Vite strips types without checking them, so this matters for your editor
and `tsc`, not for the build. Map the alias, include the vendored runtime,
and exclude the renderer folders for frameworks you haven't installed (they
import packages your app doesn't have). Each config below is complete; merge
it into yours if you already have one.

<Frameworks>
<Tab value="React">

```json title="tsconfig.json"
{
    "compilerOptions": {
        "target": "ESNext",
        "module": "ESNext",
        "moduleResolution": "bundler",
        "strict": true,
        "skipLibCheck": true,
        "noEmit": true,
        "jsx": "react-jsx",
        "paths": {
            "@mesh": ["./vendor/ethanbarlo/mesh/resources/js/index.ts"],
            "@mesh/*": ["./vendor/ethanbarlo/mesh/resources/js/*"]
        }
    },
    "include": [
        "resources/js/**/*.ts",
        "resources/js/**/*.tsx",
        "vendor/ethanbarlo/mesh/resources/js/**/*.ts",
        "vendor/ethanbarlo/mesh/resources/js/**/*.tsx"
    ],
    "exclude": [
        "node_modules",
        "vendor/ethanbarlo/mesh/resources/js/vue",
        "vendor/ethanbarlo/mesh/resources/js/svelte"
    ]
}
```

Install the React types with `npm install -D @types/react @types/react-dom`.

</Tab>


## Production build

```bash
composer install --no-dev --optimize-autoloader
npm ci
npm run build
```

Each component becomes its own chunk in `public/build`, and a page fetches a
component's chunk the first time it renders that component. Pages without
islands never download component code. With `debug: import.meta.env.DEV`,
production builds log nothing.
